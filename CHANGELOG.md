# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

### Removed
- **[issue-746] Removed the size optimizer's unused balance-poll re-evaluation path** — `src/size-optimizer.js` exported `updateBalance()`/`evaluateForBalance()`, a reactive path meant to re-evaluate sizing on a live balance swing between cycle completions, but no engine code ever called it — `src/regime-engine.js` only ever drives sizing through the cycle-completion path (`recordCycle()`), and #694 deliberately left it unwired when it fixed that path's balance-feed bug. Rather than build a new polling trigger for a feature nothing asked for, it and its now-dead `BALANCE_CHANGE_THRESHOLD` constant are deleted; sizing re-evaluation is cycle-based only. `tests/size-optimizer.test.js` no longer exercises it, and its `adjustmentHistory`-cap regression coverage now drives the cap through `recordCycle()` instead.

### Changed
- **[issue-700] Open Orders buy linkage no longer depends on the Filled Orders cycle toggle** — Expanding a resting take-profit in the Regime dashboard's Open Orders table showed a different set of buys depending on whether the Filled Orders section below was set to "All Cycles" or "Current Cycle". It now always reads the full fill ledger. The fallback for older core take-profits with no recorded buy link now only looks at the live cycle, so it never lists a previous cycle's buys. Internally, the Open Orders and Filled Orders sections were extracted from `RegimeDashboard.jsx` into `regime/OpenOrdersTable.jsx` and `regime/FilledOrdersSection.jsx`, and their pairing logic moved into pure, unit-tested modules. `openOrderRelations.mjs` reuses `shared/cycle-pairing.mjs` for ledger linkage, and `deriveDryRunFillGroups` in `regimeFillGroups.mjs` replaces the dry-run walk that ran on every render. The fill scans now run once per fill snapshot, not once per open take-profit on every ~1s status tick.
- **[issue-725] Shrank the order-executor contract to methods `regime-engine.js` actually calls** — follow-up to #678's cleanup: `checkInvariants`, `getSummary` (the executor's own status-string getter, not `ladderCalculator`/`riskManager`'s) and `clearPendingOrders` were required by every executor's contract (`REQUIRED_EXECUTOR_METHODS`) but had zero production callers anywhere in `src/`, `scripts/`, `admin/`, or `server.js`, and zero method-specific test coverage — `regime-engine.js` already enforces `maxOpenOrders` inline and tracks TP/body state through its own persisted `positionState`, making these three pure duplicates. Deleted from both `src/order-executor.js` and `src/dry-run-executor.js`, the contract, and the `OrderExecutor` typedef. `getActiveTpOrderId`, `isBodyTpOrder` and `getBodyByTpOrderId` had the same zero-production-caller finding, but unlike the other three they carry real, still-valuable regression coverage with no clean production-path substitute (TP-placement concurrency safety in `tests/race-conditions.test.js`; the dry-run cost-basis round-trip suite in `tests/dry-run-executor.test.js`) — so instead of deleting them, they were dropped from `REQUIRED_EXECUTOR_METHODS`/the typedef's required properties and stay implemented, exported, and documented as optional (a new `TEST_ONLY_EXECUTOR_METHODS` export in `src/executor-contract.js`, with a regression test guarding both directions). `tests/executor-contract.test.js`'s `ALLOWED_UNCALLED_BY_ENGINE` allowlist is now empty.
- **[issue-727] Split `config-utils.js` into three focused modules (no behavior change)** — followed up on #689's deferred step 4: `REGIME_FIELD_RULES`/`hasRegimeFieldTypes`/`validateRegimeConfig` moved into `src/config-validator.js` (which already owns every other regime-shape schema), and the backup-archive snapshot/reconstruct logic (`buildConfigSnapshot`, `validateConfigSnapshot`, `reconstructConfigOverride`, `diffSnapshotAgainstConfig`, and the `SNAPSHOT_*`/`CONFIG_SNAPSHOT_*` constants) moved into a new `src/config-snapshot.js`. `config-utils.js` re-exports every moved name so existing callers (`backup-service.js`, the route files, and the existing test suites) are unaffected. Pure code organization — `config-utils.js` was still mixing file IO/mtime cache, fund topology, per-domain getters/setters, regime value rules, and archive snapshot/reconstruction in one ~2,240-line file.
- **[issue-738] Test suite no longer hangs under concurrent `npm test` runs** — `tests/restore-writer-quiescence.test.js`'s "engine IPC server enforces the maintenance window" test bound a fixed TCP port (45529), so a second concurrent test run (e.g. two `/do:next` worktrees, or a developer running tests in two terminals) hit `EADDRINUSE` and then hung indefinitely waiting on a socket event that never arrived, stalling the whole suite. It now reserves an OS-assigned ephemeral port the same way `tests/engine-trade-event-bridge.test.js` already does, so concurrent full-suite runs no longer collide.
- **[issue-689] Unified fund-config write topology and removed silent-overload traps in `config-utils.js`** — `updateFundConfig` and `updateRegimeConfig` each re-implemented the same legacy-flat-vs-nested write dance independently, and had already diverged: only `updateFundConfig` cleared a fund's deletion tombstone (#441), so a regime config save on a re-added (previously deleted) pair silently failed to persist — `normalizeExchangeBlock` kept hiding that pair on every subsequent read even though the write itself succeeded. Both writers now share one `mutateFundBlock(exchange, pair, mutator)` helper, so `updateRegimeConfig` clears the tombstone exactly like `updateFundConfig` always has. Also replaced the `typeof`-dispatched 2-or-3-argument overloads on `updateRegimeConfig`, `setExchangeEnabled` and `setExchangeDryRun` — where a caller that ended up passing an `undefined` pair silently fell through to the wrong (default-fund) branch and dropped the intended update — with explicit, single-purpose functions: `updateRegimeConfig(exchange, pair, updates)`, `setFundEnabled(exchange, pair, enabled)` and `setFundDryRun(exchange, pair, dryRun)` now throw a `TypeError` on a missing/empty pair instead of silently misrouting the write, with thin `updateExchangeRegimeConfig(exchange, updates)` / `setExchangeEnabled(exchange, enabled)` / `setExchangeDryRun(exchange, dryRun)` aliases kept for legacy default-fund callers. Removed the dead, already-drifted `validateExchangeConfig` (superseded by `EXCHANGE_CONFIG_SCHEMA` in `src/config-validator.js`; it was exported but exercised only by its own tests). Updated all callers (`src/routes/exchange-routes.js`, `src/dca-converter.js`) to the explicit-pair form. Added regression coverage for the tombstone fix and the new `TypeError` guards in `tests/config-utils.test.js`. Moving `REGIME_FIELD_RULES`/`validateRegimeConfig` into `config-validator.js` and extracting `config-snapshot.js` (the file's remaining size/cohesion concerns) is tracked separately in #727.
- **[issue-678] Removed dead, contract-required, drifted order-executor methods** — `refreshStaleOrders`, `atomicReplace` and `cancelAllBodyTpOrders` were required by every executor's contract (`REQUIRED_EXECUTOR_METHODS`) and implemented in both `src/order-executor.js` and `src/dry-run-executor.js`, but nothing outside their own test suites ever called them; `refreshStaleOrders` duplicated the same per-order stale-timeout cancel logic already live in `scheduleStaleOrderTimeout`, with a bug class (an unguarded `getOrder` in its sweep loop) the live path doesn't have. Deleted all three (plus dry-run's dangling `cancelAllSatelliteTpOrders` alias) from both executors, the contract, and the `OrderExecutor` typedef; also fixed the typedef's stale `placeTakeProfitOrder` field name (`wasUpdated` → `updated`, matching the actual return shape) and a stale doc reference in `docs/adaptive-stale-timeout.md`. The partial-fill-routing and per-order-adaptive-timeout test coverage those two deleted sweeps carried was ported onto `checkPendingOrderFills` / `scheduleStaleOrderTimeout`, the live paths that already implement the same behavior, and `tests/executor-contract.test.js` gained a regression test asserting every required method is actually called by `src/regime-engine.js` (or explicitly allowlisted), so a future required-but-unused method fails loudly instead of drifting silently the way these three did.
- **Coinbase Advanced API requirement clarity in setup guide and UI** — Updated the setup guide in `README.md` and the admin keys configuration UI (`admin/src/components/KeysConfig.jsx`) to make it explicitly clear that operators must use Coinbase Advanced API / Coinbase Developer Platform (CDP) API keys, not the regular or legacy Coinbase API (`coinbase.com/settings/api`). Added direct CDP portal links (`https://cloud.coinbase.com/access/api`), format descriptions for the EC private key PEM and `organizations/...` key name, a prominent warning notice in the Keys Config UI, and clear rejection guidance in `src/routes/keys-routes.js` when regular `apiKey`/`apiSecret` fields are submitted.
- **[issue-582] Shared cycle-recalculation rules between preview and apply** — Operator cycle recalculation previously maintained duplicate implementations of completion heuristics (`0.5` sell ratio), orphan fill recovery (`cycle-${ts}-recovered-${i+1}` naming), and fill grouping across `recalculateCycles` and `previewRecalculateCycles`. Extracted `CYCLE_COMPLETE_SELL_RATIO`, `isCompletedCycle`, `splitOrphansIntoCycles`, and `groupFillsByCycle` as shared module-level helpers in `src/fill-ledger.js`, ensuring the preview and apply share identical logic and produce matching cycle details without preview mutating ledger state. Added regression and parity test coverage in `tests/fill-ledger.test.js`.
- **[issue-581] `ingestNewFillsForOrder` returns a named `outcome` instead of three ambiguous counts** — Callers used to ignore `{fetched, fillsCount, ingestedCount}` and re-read `trackedOrder.lastIngestedFilledSize` (or re-query the ledger) to decide what just happened, while four hand-written reason ternaries labelled the same failure differently across partial vs FILLED retry chains. The helper now returns `{outcome, recordedSize, ingestedCount, error?}` with `already-covered` / `covered` / `short` / `no-fills-yet` / `fetch-failed` / `persist-failed`, call sites branch on that outcome, and both retry chains share one `INGEST_RETRY_REASON` map. Retry scheduling conditions are unchanged. Coverage in `tests/market-data-service.test.js`.
- **[issue-580] Named the regime engine's mutual-exclusion protocol** — merge, reconcile, fill, and entry guards lived as eight bare closure flags and four hand-written `||` predicates scattered through `src/regime-engine.js`, with reentrancy spelled `opts._noLock` and deadlock-freedom only in comments (a fill busy-waits up to 15s for a merge; a merge must never wait on fills). Extracted the protocol into `src/engine-locks.js` (`createEngineLocks()`): `withMergeLock` is reentrant (collapse-all no longer passes `_noLock`), `withFillGate` owns the bounded merge wait and timeout warning, `isMutatingStructure` / `isMutatingPosition` / `describeBusy` replace the inline busy checks, and the `_test` setters still drive the same interleavings. No change to predicates, operator refusal messages, or the 15s fill-wait bound.

### Added
- **[issue-609] Coinbase drift-sweep regression coverage** — Verified cursorless paginated fill responses terminate safely and still produce the normalized fill data required for Coinbase ledger-drift detection.
- **`src/engine-liveness.js` — an authoritative "is this fund's engine live?" check** — the repair scripts must never write a fund's `fill-ledger.json` / `regime-state.json` under a running engine, which holds both in memory and rewrites them on its own timer. They originally gated on the mtime of `regime-engine-running.json` with a 5-minute staleness window, which was wrong twice: that file is written once at start and once at stop (`engine-lifecycle-handlers.js:119,190`), so its mtime is the *start* time and any engine up longer than the window read as "stopped"; and an **absent** file read as "stopped" too — the state of every fund whose directory was recreated, i.e. exactly when a repair runs. (Live proof: `coinbase/BTC-USDC` had no flag file at all while its engine was serving IPC.) The check now trusts the flag only when it positively records `running: true`/`false`, and otherwise probes the exchange's engine IPC port, failing closed when liveness is unknowable. Covered by `tests/engine-liveness.test.js`.
- **Periodic exchange-vs-ledger drift detection** — nothing in the running system ever compared the fill ledger against the exchange, so a dropped fill was silent and permanent; `syncFills` existed in `src/sync-fills.js` but had no caller anywhere. The engine now runs `sweepLedgerDrift` on its own timer (`fillDriftSweepMs`, default 30 min, `0` disables; only for adapters advertising `capabilities.fillReconciliation`), logging `🩸 Ledger drift: N exchange fill(s) ... unaccounted` and surfacing `fillDrift` on `getState()`. It is deliberately **detect-only** — auto-ingesting historical fills into a live engine would re-open cycle and cost-basis accounting mid-flight — and runs outside the reconcile lock so a slow trade fetch can never stall reconciliation.
- **Position-coverage invariant on the drift sweep** — a complete ledger does not imply a complete position model. `heldOpenBuyCostBasis` decides a buy is closed on a boolean (`sellOrderId` set and that sell has fills) with no quantity check, and `sellOrderId` is re-stamped across merges and TP replacements — so a buy order only partly sold counts as fully closed and its unsold remainder leaves the model entirely: in no body, no take-profit, absent from the UI. gemini/ETHUSD was carrying 1.14 ETH in that state even after its ledger matched the exchange exactly. `sweepLedgerDrift` now also asserts the one identity that cannot lie, `balance == Σ body.assetQty + reserves`, logging `⚖️ Position coverage gap: …` and surfacing `positionCoverage` on `getState()` when the remainder exceeds the exchange's minimum tradeable size.
- **`scripts/adopt-untracked-asset.js`** — operator repair for a position-coverage gap: folds base currency the account holds but no body or reserve accounts for into a new celestial body, so the engine manages it again. The untracked amount is read off the `balance == Σ body.assetQty + reserves` identity rather than the buy→sell linkage (which cannot support it), and its cost basis comes from a FIFO replay of the ledger, spread pro rata over every unit held. Dry-run by default; prints the resulting take-profit against spot — below-spot TPs are placed `postOnly: false` and cross immediately, so the run sells real asset — and `--apply` backs up `regime-state.json`, refuses to write under a live engine heartbeat, and aborts unless the new body closes the gap exactly.
- **`scripts/backfill-missing-fills.js`** — operator repair for a drifted ledger, on any exchange/pair. Ingests every exchange fill the ledger is missing, and replaces pseudo-fill rows (`synthetic-<orderId>`, `consolidated-sell-<ts>`) with the real exchange fill they stood in for, moving their `bodyPnl`/`bodyHoldbackAsset`/linkage annotations onto the surviving row first. Recovered fills inherit the cycleId of their own order (an order cannot straddle a cycle) rather than running `recalculateCycles`, which would renumber settled history. Dry-run by default; `--apply` backs up the ledger, refuses to write under a live engine heartbeat, and aborts unless the repaired ledger's net asset matches the exchange and booked realized P&L is unchanged.

### Fixed
- **[issue-752] Re-imported fills of a body's own orders now keep their body, and a missed partial buy now grows its body** — follow-up to #705: when the fill sync re-imports a missed row of a body's take-profit sell, cycle recalculation moved it into the right cycle but left it looking like an old-style core sell. That row was then counted in the core position and cycle stats, and the auto-link repair could book unrelated core buys against it. The row now inherits its order's body and P&L annotations (P&L is still counted once per order). A re-imported take-profit with no sibling rows takes its body ownership from the body buys linked to it, and auto-link only uses a re-imported sell as a cycle's close when core buys, and no body buys, link to it. Rows an earlier recalculation already moved are repaired the same way. A missed partial row of a body's own buy order now also grows that body, so its take-profit is re-sized for the full position. At startup (once the engine is live) and after a recalculation, the body is extended with its take-profit cancelled first and then re-placed at the new size. The growth is guarded: it applies only to the engine's own order recorded by exactly one live body, skips orders holding a synthetic gap fill, runs one extend per body at a time, is idempotent, and never exceeds the recovered rows' size.
- **[issue-673] A polled buy fill that fails processing is now retried automatically instead of going missing until restart** — On exchanges with no order-events WebSocket (Gemini, Crypto.com), the polling fill check drops a filled buy from its own tracking the moment it detects it, before handing the fill off for processing. Issue #679 already added a bounded retry inside that hand-off, but once it gave up (a transient API error, a full disk, etc.), nothing else re-checked that buy until the engine restarted — the bought asset sat invisible to the dashboard and still counted as deployed capital with no position or take-profit behind it. The periodic reconcile pass now sweeps for exactly this: a saved pending buy/ladder order the exchange already shows as done but that fell out of the engine's own order tracking, and books it (or safely clears it, if it turned out to be an empty cancel) without waiting for a restart. Added regression coverage in `tests/reconcile-orphaned-entry-sweep.test.js`.
- **[issue-742] A dry-run reset now clears the drawdown pause, and a depleted-equity pause is now visible on the dashboard** — follow-up to #693's drawdown guard: `resetDryRun()` replaced the position state but left the risk manager's in-memory drawdown peak/pause untouched, so the next metrics tick wrote the stale peak and pause straight back into the freshly-reset dry run. `resetDryRun()` now also resets the drawdown tracker. Separately, when the guard fails closed because fund equity is depleted (a deliberate choice — the time-based auto-reset does not apply to a non-positive peak, since re-basing to it would be meaningless), the dashboard's Risk Limits panel now shows an explicit "Equity depleted — no auto-reset" notice instead of leaving the operator to guess why Resume keeps failing, and a failed manual resume now surfaces the engine's actual reason (e.g. "Fund equity is depleted...") instead of a bare HTTP status.
- **[issue-671] Restarting the engine while a buy was partly filled no longer strands the filled part** — On startup, an entry order still resting on the exchange with some of it already filled (whether the engine was tracking it or adopted it as an orphan) had that filled part recorded in the fill ledger but never placed in a position: when the order later finished filling, only the new part got a position and take-profit, so the earlier part was never sold, never shown, and the order was counted as two buys. Startup now books the filled part through the normal fill path, so it opens a position with its take-profit right away and the rest of the order joins that same position when it fills; an adopted orphan order is also saved so it is still tracked after the next restart. A filled part stranded this way by an earlier restart is also picked up, without double-counting the buy, as long as its order is still open at the next restart. And if part of an order was already sold through its own take-profit while the rest kept resting, neither startup nor the first check after a restart books that sold part a second time as a new position.
- **[issue-750] A foreign sell's effect on the position is surfaced, not guessed** — follow-up to #672. A sell the engine did not place (manual sale, DCA/manual-trades tooling, a script) is tagged `untrackedSell` and closes no cycle, but with no open bodies it may have drawn down the legacy core position (`positionState.totalAsset`/`totalCostBasis`) — or the zero-cost reserves; the fill alone cannot say which. Rather than attribute it (either guess corrupts cost basis or reserves P&L), the engine now leaves the position model untouched, logs a `⚖️` operator-review warning when a held position may have been consumed, and breaks the sale out of the ledger: `getDerivedRealizedPnL()` reports `untrackedSellQty` (counted once per order, including fill rows ingested after the tag) and the drift sweep's `positionCoverage.ledger.untrackedSold` says how much of a negative coverage gap those sells explain, also appended to the `⚖️` coverage-gap log lines. Regression coverage in `tests/partial-buy-consumption.test.js`.
- **[issue-718] A take-profit that fills while a merge or roll-up is cancelling it no longer counts its holdback twice** — when a body's take-profit executed its full planned size during a buy-merge or roll-up cancel, the holdback was booked as reserves while the same coins also stayed in the still-listed body, which then re-listed them for sale (or left them as dust). The P&L header's reserves and the body's inventory both counted those coins. The filled body is now closed exactly like a normal take-profit fill: its holdback moves to reserves only, the body is removed (or, if another buy was folded onto it in the meantime, keeps only that buy), so bodies plus reserves match the fill ledger's net position again.
- **[issue-705] Fills the engine missed during downtime inside the live cycle now count toward that cycle** — After #675, `recalculateCycles` put every null-cycle fill (re-imported by `sync-fills` / manual-trade import) into its own recovered cycle, so a buy that genuinely filled inside the live cycle while the engine was down never counted toward `cycleBuys` (letting the per-cycle entry limit be exceeded) or the live cycle's totals. Recalc now places null-cycle fills in existing cycles first, in both the preview and the applied path: linked fills (the same order, or a buy's `sellOrderId` / `consumedBy` pointing to a sell) join their order's cycle and always move together, so a buy is never split from its sell. Unlinked buys go into the live cycle only when every one of them is at or after the cycle's start time and no unplaced orphan sell comes after them, so an unlinked manual round trip stays together as one cycle. An unlinked sell never joins the live cycle by time, because the engine's own TP sells are already placed by their links; a manual-import pair must not complete the live cycle or shrink its position. Anything ambiguous, containing an unlinked sell, straddling that start time, or older still goes to a recovered cycle as before. A recovered partial row of an already-annotated buy order inherits that order's ownership annotations (body, TP link, consumption). Cycle completion is now checked *after* this placement, so preview and apply agree when a placed sell completes a cycle. A cycle reset now saves its start time (`positionState.activeCycleStartedAt`), so a still-empty post-reset cycle keeps its start boundary across restarts (a saved start time is authoritative; only without one is the cycle's earliest fill used, and an empty cycle gets nothing). After a recalc that adds fills to the live cycle, both the boot path and `recalculateAndRefresh` re-derive `cycleBuys`, the position totals and (forward-only) the entry clock from the ledger. A stopped-fund recalc apply saves the new `cycleBuys` too. Fills placed by timestamp only are marked `cycleAttribution: 'timeframe'`. They count toward `cycleBuys` but stay out of the core position totals, legacy-TP `sellOrderId` linking, recalc's completed-cycle auto-link, and boot's orphan-buy-to-body recovery. `sync-fills` also imports manual trades, and the engine must never place a TP for those automatically. Regression coverage in `tests/fill-ledger.test.js`, `tests/reset-cycle-buys.test.js` and `tests/engine-recalculate-handler.test.js`.
- **[issue-697] Filled Orders grand total now always matches the Position card's Realized P&L** — the two numbers came from separate pairing rules and disagreed for sells without an engine P&L annotation (the dashboard prorated cost while the engine charged the full linked cost), for buys still linked to a replaced take-profit order (the dashboard followed the body to the real sell; the engine counted them as open and the sell as unpaired), and for legacy/manual buys with no order id (the dashboard lumped them all onto one sell). Both now use one shared rule set: annotated P&L taken once per order, otherwise sale proceeds minus linked buy cost prorated by the quantity sold, replaced-TP buys followed through their body, no-order-id buys kept separate, and a recorded holdback always honored. Realized P&L for sells the engine annotated (the normal case) is unchanged; legacy unannotated rows may shift to the prorated figure.
- **[issue-672] A manual or external sell no longer gets booked as a completed cycle** — Between celestial cycles (no open bodies), any sell on the fund's product — a manual sale of reserves in the exchange UI, the DCA/manual-trades tooling, a script — was treated as the engine's own take-profit: its full sale value was credited to the fund's deployment budget as "profit", the completed-cycle count went up, the cycle (and its ladder) was reset, and a closed trade with zero cost basis and negative holdback was recorded. The cycle-closing path now runs only for the engine's own take-profit order; any other sell is tagged as an untracked sell and logged, with no budget credit, no cycle reset, and no closed-trade entry. Retries of a genuine take-profit close still finish idempotently.
- **[issue-680] Gemini funds no longer trip SAFE mode from their own request-throttle queue** — The health monitor's REST latency measurement for Gemini calls included time a call spent waiting in the adapter's own client-side throttle queue (and in its 429 backoff), not just the exchange's actual response time. A burst of concurrent private calls — many bodies reconciling on the same tick — inflated the measured average latency past the SAFE-mode threshold even though the exchange itself was responding normally, blocking new entries until the burst cleared and the average recovered. Queue/backoff wait time is now tracked separately and excluded from the latency recorded for health monitoring, so a large concurrent burst no longer misreads as exchange slowness. Added regression coverage in `tests/health-monitor.test.js`.
- **[issue-684] Gemini's untracked-sell-order safety warning can now actually fire, and Coinbase's open-order size now reflects what's still on the book** — `getOpenOrders()` reported a different `size` shape on each exchange: Gemini's mapper set no `size`/`price` at all, and the orphan-sell detector's `o.size > 0` gate silently evaluated `undefined > 0` as `false`, so the operator-facing "Untracked sell order on exchange — manual review required" warning could never appear on Gemini. Coinbase reported `size` as the order's *original* placed quantity rather than what remains unfilled, understating how much a partially-filled order had already sold. All three adapters (Coinbase, Crypto.com, Gemini) now report `size` as the remaining unfilled base quantity, plus `originalSize` (what the order was placed for) and `price`, matching the shape Crypto.com already used. Added regression coverage in `tests/adapter-open-orders-shape.test.js`.
- **[issue-694] Auto-managed sizing no longer strangles a fund's deployment cap over time** — With `sizeAutoManaged: true` (opt-in, off by default), every cycle completion fed the size optimizer its own configured deployment cap as if it were the real exchange balance, so each evaluation recomputed the cap as ~90% of itself — a compounding shrink (observed: $1005 → $905 → $819 → … → $456 over 40 cycles) that also dragged the base order size down to its floor, regardless of actual fund performance. The optimizer is now fed the real available exchange balance at cycle completion, and no longer proposes a sizing change at all until a real balance reading has actually been observed (a temporarily unavailable balance fetch is skipped rather than treated as zero). Regression coverage in `tests/size-optimizer.test.js` and `tests/size-optimizer-balance-feed.test.js`.
- **[issue-693] The max-drawdown limit now actually pauses new buys** — `maxDrawdownPercent` and `drawdownResetHours` could be set in the config editor but did nothing: the engine never measured drawdown, so the pause never triggered, entries kept going during a crash down to the other caps, and the dashboard's drawdown bar always read 0%. Drawdown is now evaluated every minute and blocks new reactive entries and new ladders once the limit is hit (orders already resting are left alone), resuming automatically at half the limit, after `drawdownResetHours`, or via the dashboard's Resume button. Drawdown is measured on fund equity — deposited capital, minus what's tied up in open positions, plus realized profit, plus all held coins (open positions and holdback reserves) at the current price — so a normal take-profit converting coins to cash never reads as a drawdown, and deposits or withdrawals re-base the peak instead of looking like gains or losses. The peak, the active pause, and the worst drawdown seen now survive engine restarts, and the manual Resume sets the new peak in the same unit (previously it used a P&L figure unrelated to the tracked value).
- **[issue-681] Gemini/Crypto.com not-found detection now matches the errors those adapters actually throw** — The shared `isOrderNotFoundError` predicate only recognized axios-shaped `err.response.status`/`err.response.data.code`, which neither `fetch`-based adapter ever sets, so a truly-gone order on Gemini or Crypto.com was always read as a transient lookup failure: startup restored tracking for a dead take-profit, and reconcile logged an error every tick instead of clearing and re-placing it, leaving the position unprotected until an operator intervened. Both adapters now tag a definitive not-found (HTTP 404, or the exchange's own reject code/reason) on the thrown error as `err.orderNotFound` before it propagates, and the shared predicate checks that flag (with a narrow message-shape fallback). Coinbase is deliberately left unflagged — its eventually-consistent history endpoint can briefly 404 on a still-live order, and flagging it would risk clearing a healthy take-profit. Replaced the old synthetic-error test cases with adapter-level tests that stub `global.fetch` and drive the real error-construction path in `tests/shared-utils-order-not-found.test.js`.
- **[issue-677] Cycle recalculation no longer closes a still-open body's buy against a different body's sell** — `recalculateCycles`'s auto-link step stamped every buy without a `sellOrderId` in a "completed" cycle (sells covering at least half the cycle's buy volume) with that cycle's first sell order. In celestial mode a cycle can hold many bodies at once, and it counts as "completed" once that ratio crosses 50% even while other bodies in the same cycle are still open with no take-profit placed yet — a min-size body, a failed placement, or a crash between fill and TP. The false link zeroed that body's held cost basis, inflating unrealized P&L and APY by the body's full cost and showing its buy under the wrong cycle's sell in the Filled Orders table; the link was permanent for a body that never gets a TP. Auto-link now applies only to legacy (non-body, non-satellite) buys and never links inside the ledger's still-live cycle — body/satellite linkage is owned by TP placement and boot repair, not this heuristic. Added regression coverage in `tests/fill-ledger.test.js`.
