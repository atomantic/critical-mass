### Fixed

- **[issue-495] Regime settings reject wrong primitive types before persistence or live updates** — Validate every supported numeric field as a finite number, preserve existing bounds and zero sentinels, and reject malformed regime containers across all save paths so drawdown limits cannot be disabled by invalid input.
- **[issue-431] A failed or interrupted backup restore no longer leaves the data directory as a mixed generation** — `restoreBackup` in `src/backup-service.js` recursively `fs.copyFileSync`'d every staged file straight over its live destination, so a copy error (ENOSPC, EACCES) committed every preceding file at the archive's generation while later files stayed current, with no rollback copy, no marker, and the extraction directory leaked; a process death mid-overwrite could additionally leave a truncated ledger or regime-state file, and the next start had nothing on disk telling it the accounting data was incoherent. New `src/restore-apply.js` applies a staged archive as one recoverable transaction: the whole staged set is validated first (readable regular files only — a symlink smuggled into an archive is now refused before any write), every destination that will be replaced is copied aside under a durably-fsynced rollback journal (`data/.restore-journal.json`), each replacement is a same-directory temp file + atomic `rename` (so a reader sees the old bytes or the new bytes, never a truncated file), and the journal flips to `committed` only once every destination succeeded. A mid-apply failure reverts every destination to its pre-restore bytes and removes files the attempt created; a rollback that cannot itself complete retains the journal and originals and returns `code: 'restore-incomplete-recovery'` through `src/restore-coordinator.js` and `src/routes/settings-routes.js` so `admin/src/components/BackupRestore.jsx` tells the operator to retry rather than presenting a plain failure. The reconstructed `config.json` override (#430) is now staged into the same transaction instead of being written after the copy, so config and data can no longer diverge. `guardIncompleteRestore` runs in `server.js` and `engines/coinbase-engine.js` before migration and before any fund loads its ledger or regime state: an interrupted restore finishes its rollback there, and one that cannot be rolled back exits the process instead of trading on a half-restored ledger. Restore bookkeeping is also excluded from new archives, so a stale journal can never ship inside a backup. Added `tests/restore-transactional-apply.test.js` (16 cases: atomic-replacement proof, injected failures at each stage, incomplete-recovery retention, simulated restart recovery, and an end-to-end create/fail/restore coherence check).
- **[issue-454] Recalculate, DCA conversion, and manual-buy-import flags now reject non-boolean values instead of forwarding them into a destructive branch** — `apply` (recalculate), `preview`/`merge` (DCA conversion), and `createBody` (manual buy import) each select a preview-vs-mutate path downstream, but `src/routes/regime-routes.js` destructured them straight off `req.body` with only a default, so a request like `{ "apply": "false" }` passed the truthy string on to IPC and the `regime:recalculate`/`regime:convert-dca` handlers in `engines/coinbase-engine.js` (and `importBuy` in `src/manual-trade-import.js`) branched on it as truthy — silently applying a recalc, executing a conversion, or creating a live-TP body when the caller intended read-only preview. Added a shared `readBooleanFlag` helper to `src/shared-utils.js` that accepts only a literal boolean or the field's absence (rejecting strings, numbers, arrays, objects, and `null` with a 400/`{success:false,error}`), applied at both the gateway routes and the corresponding IPC/importer handlers so a direct IPC caller can't bypass the gateway's check. Omitting a flag keeps its documented default (`apply=false`, `preview=true`, `merge=false`, `createBody=true`) exactly as before. Added regression coverage in `tests/regime-routes-control.test.js` (route-level, proving IPC is never reached for a rejected flag), `tests/manual-trade-import.test.js` (proving a rejected `createBody` touches neither the ledger nor the store), and `tests/shared-utils-read-boolean-flag.test.js`.
- **[issue-452] Regime config value validation now applies consistently across every save path, not just the dedicated regime route** — `PUT /api/:exchange/regime/config` was the only entry point that ran a nested `regime` update through `validateRegimeConfig` in `src/config-utils.js`; `PUT /api/:exchange/config` (`src/routes/exchange-routes.js`) and legacy `PUT /api/config` (`src/routes/legacy-routes.js`) only ran `sanitizeRegimeConfig`, which drops unknown keys but never checks a known key's value, and `POST /api/:exchange/funds`'s regime seed skipped sanitization entirely. A payload like `{ "regime": { "maxDrawdownPercent": 999 } }` was persisted and forwarded to the live engine (`regime:update-config` IPC) through any of those three surfaces even though the dedicated route would reject it — defeating `src/risk-manager.js`'s drawdown-pause safety check with a value outside the documented 10-30% range. Added `validateAndSanitizeRegimeConfig` to `src/config-validator.js`, a single sanitize-then-validate step (dropping unknown keys per the existing round-trip contract, then checking known values via `validateRegimeConfig`, filling in the fund's current value for whichever half of a cross-field pair — e.g. `macroAccumulationThreshold`/`macroMarkupThreshold` — a partial update doesn't touch) reused by all four entry points: the dedicated regime route (replacing its inline duplicate of the same logic), the full-config PUT and its legacy alias, and fund creation's regime seed. Unknown keys are still dropped rather than rejected — stale persisted keys remain permanently saveable — but out-of-range or cross-field-invalid values now 400 with zero writes and zero IPC calls on every path. Added parity regressions to `tests/exchange-routes-config.test.js`, `tests/legacy-routes.test.js`, `tests/exchange-routes-lifecycle.test.js`, and `tests/regime-routes-config.test.js` (including a partial-update cross-field case), and confirmed the existing stale-key round-trip tests still pass unchanged.
- **[issue-455] Config Save and the Enabled/Dry Run toggles now share one write gate instead of racing each other** — `admin/src/components/ConfigEditor.jsx`'s `handleSave` (full-form PUT) and `persistToggle` (the PATCH/PUT autosave behind `handleToggleEnabled`/`handleToggleDryRun`) were independent write paths for the same configuration: only the Save button was disabled while a save was in flight, so the Base Size input and both top-level switches stayed editable, and a slow save's response unconditionally adopted onto whatever the form held and cleared `isDirty` — silently discarding an edit typed during that request. Conversely, Save stayed clickable while a toggle's optimistic value was still unconfirmed, letting a full save submit it before the PATCH resolved. Both handlers now share one `pendingWriteRef` counter, checked synchronously at the top of `handleSave`, `handleToggleDryRun`, and `handleToggleEnabled` before either sets any state — so a write in flight (of either kind) makes the other three entry points no-ops, even against a rapid double-click that outruns a re-render. A new `locked` render-state boolean (`saving || toggleBusy`) drives `disabled` on both `ToggleSwitch`es, Save, and Reset, and wraps the DCA fields and every regime settings card (excluding the Aggressiveness Presets editor, which keeps its own independent `savingPresets` gate) in a native `<fieldset disabled={locked} className="contents">` — one boolean disables every input/select/checkbox in the fund-config area via the browser's own form-disabling semantics, with `display:contents` keeping the fieldset out of the existing grid/flex layout. The failed-write rollback in `persistToggle`, the persisted-but-not-applied warning/restart-required messaging in both `handleSave` and `persistToggle`, and the background-refresh sync effect's in-flight skip (renamed from `togglePendingRef`, now also covering full saves) are all unchanged. Added `tests/config-editor-write-gate.test.js` (source-text assertions, matching the no-jsdom convention established by `tests/fund-operation-modal-dialogs.test.js`) covering the shared-ref guards, the render-state wiring, the fieldset boundaries around (but not including) the presets editor, and that every distinct success/warning/error message text survived the refactor.
- **[issue-451] LogViewer's Flush button no longer reports success when the PM2 flush actually failed** — `logs:flush` in `src/log-stream-manager.js` (extracted from `server.js` by #448) already emitted `logs:flushed` with `success:false` on a nonzero `pm2 flush` exit or a spawn error, but `useLogStream.js`'s handler discarded that flag and just cleared `flushing`, so `LogViewer.jsx` treated every flushing→not-flushing transition as a success and always showed a "Logs Flushed" toast — a real backend failure was silently reported as success. `useLogStream.js` now tracks the in-flight flush request (`pendingFlushRef`) and exposes a `flushResult` (`{ success, reason? }`) alongside the existing `flushing` boolean; `LogViewer.jsx` renders a success toast only for `success:true` and an error toast ("Flush Failed") for `success:false`, releasing the button either way. The accept/reject decision and toast copy are pure functions in the new `admin/src/utils/flushResult.mjs` (`shouldAcceptFlushResult`, `flushResultToast`), so a duplicate completion (nothing pending), a response for the wrong process, or a stale response after the selected process changed are all ignored rather than applied. `src/log-stream-manager.js`'s flush handler now settles at most once per request (guards a spawn `error` immediately followed by `close`) and reports a safe `reason` — `exit code N` or `spawn failed: <message>` — with no raw `pm2` stdout/stderr forwarded to the client (the previously-collected but unused `output` buffer is removed). A flush still pending when the socket disconnects, or when the operator switches to a different process mid-flush, now clears `flushing` instead of leaving the button stuck on "Flushing..." forever; disconnect resolves it as an explicit failure toast, while a process switch clears it silently (no stale toast for a request nobody is looking at). Added flush-result coverage to `tests/log-stream-manager.test.js` and a new `tests/log-flush-result.test.js` exercising the frontend pure logic directly — no real PM2 flush, socket, or React render involved.
- **[issue-430] Backup archives now carry the fund configuration they were taken with** — `createBackup` in `src/backup-service.js` archived only the data directory, but `data/config.json` holds just the `computeDiff` against the machine-local base `config.json` (or, on a fresh clone, the shipped `config.example.json`) that `loadRawConfig`/`saveConfig` in `src/config-utils.js` layer against — so an install whose funds are declared in the base file produced an archive with an **empty** override and no fund identity at all. Restoring it onto a fresh clone recovered `coinbase/ETH-USDC` state files while the destination's effective config still said `BTC-USDC` at the shipped `10000` allocation, stranding the original fund and silently re-sizing capital (`src/state-tracker.js` adjusts fund size from allocation changes). Archives now include a versioned `backup-manifest.json` whose `config` is a self-contained, schema-allowlisted snapshot of the *effective* non-secret configuration — every configured pair identity with its capital settings and full regime block already materialized — built by the new `buildConfigSnapshot` in `src/config-utils.js` from the new pure `resolveFundConfig`/`resolveRegimeConfig` resolvers that `getFundConfig`/`getRegimeConfig` now share. `restoreBackup` validates the manifest with `validateConfigSnapshot` (strict allowlist: an unknown fund/regime/global key is a rejection, not a pass-through), rebuilds `data/config.json` against the **destination's** base via `reconstructConfigOverride` — tombstoning base-only pairs through the existing `deletedPairs` mechanism so they can't merge back in, and preferring a minimized override over the fully-materialized one so the restored file stays a diff rather than shadowing later base edits — and verifies in memory that replaying it reproduces the archived funds. Every failure path (malformed manifest, unsupported/future manifest version, a snapshot that would not round-trip, an unreadable destination config) returns before a single destination file is written. Secrets never enter the manifest: `notifications` (Telegram bot token) and `sentinel` (AI credentials) are excluded by allowlist and the destination's own copies are carried forward untouched. Manifest-less legacy archives are refused by default with an actionable error; the operator either supplies the source machine's base config (`legacyBaseConfig`) or explicitly opts into a data-only restore (`acceptLegacyWithoutBase`). The new `GET /api/backups/:filename/compatibility` route (`inspectBackup`) drives a read-only pre-flight panel in `admin/src/components/BackupRestore.jsx` listing the funds an archive would restore and gating a legacy restore behind an explicit acknowledgement; `src/restore-coordinator.js` now propagates the applier's own failure code and reports `configRestored`/`legacy`. Documented in `UPGRADE.md`; covered by the new tmpdir-backed `tests/backup-config-portability.test.js` (15 cases: differing destination base, nested multi-pair, legacy flat base, destination-only fund removal, minimal-diff reconstruction, secret exclusion/credential preservation, and every reject-before-mutation path).
- **[issue-472] A placement whose outcome we never learn now blocks the fund instead of being re-placed** — `placeWithUnknownReconcile` in `src/order-manager.js` returned `{ success: false }` whenever reconciliation was impossible (no client order id, an adapter with no `findOrderByClientOrderId`, or a lookup that itself failed), and `src/order-executor.js`'s ladder `.catch` folded a thrown reconcile into the same shape — the shape every caller reads as "safe to re-place next cycle" — while an accepted order could be resting live and untracked. A crash between dispatch and response left no record at all, because entry tracking starts only on success. Every fund-scoped placement (entry bid, TP, body TP, ladder rung, atomic replacement, DCA buy, fixed and Fibonacci sells) now writes a durable **placement intent** to `data/<exchange>/<pair>/placement-intents.json` *before* the POST leaves the process, via new helpers in `src/state-tracker.js`; a persistence failure returns without submitting rather than dispatching an unrecorded order. The intent is removed only on a DEFINITIVE outcome — accepted and tracked, definitively rejected by the exchange, reconciled-and-adopted, or a positive not-found — and an unresolvable outcome is kept `pending` instead, at which point `placeWithUnknownReconcile` refuses every further placement for that fund. Because the record is on disk and ownership is stamped with a per-process instance id (not a wall-clock grace period, which a sub-second crash-and-restart would sail through), the refusal survives a restart while a concurrent in-flight placement in the same process is still allowed. `src/regime-engine.js` skips entry evaluation and `src/dca-engine.js` returns `placement_unresolved` from `runIntervalCycle` while one is outstanding, leaving monitoring, fill processing, TP repair, cancels and lifecycle actions untouched. Operators see the intents in the regime dashboard's new Unresolved Placements panel (also served by `src/regime-status.js` when the engine is down, which is exactly when a dispatch-window crash leaves one) and resolve them explicitly through `POST /api/:exchange/regime/reconcile-placement-intent` or the DCA equivalent on `src/routes/exchange-routes.js`: `adopt` re-runs the authoritative client-order-id lookup and, only on a positive find, grafts the real exchange order into normal tracking via the executor's new `adoptPlacement`; `discard` clears a record the operator has verified. Nothing auto-clears on a timer or on an empty lookup, adoption is exactly-once (the disk row is removed as part of the action, so a double-clicked reconcile finds nothing), and no blind POST retries were added. A corrupt intent file fails closed — placements are refused, not waved through. New `tests/placement-intents.test.js` (27 cases, tmpdir-backed, no live exchange access) covers pre-dispatch persistence, persistence-failure-prevents-submission, the unreconcilable and inconclusive-lookup paths, repeated ticks, crash/restart recovery, ladder halt, duplicate adoption, and operator adopt/discard; `tests/ambiguous-placement-contract.test.js` and `tests/trading-structured-logging.test.js` were updated for the new pending contract.

- **[issue-448] LogViewer no longer shows "Streaming" after the PM2 log process exits** — `logs:subscribe` in `server.js` acknowledged the client and then only ever removed its `activeLogStreams` map entry when the spawned `pm2 logs` child closed; it never told the browser, so a nonzero-exit or crashed child left `LogViewer.jsx` showing a green "Streaming" dot indefinitely with the Socket.IO connection still alive. The PM2 log-child lifecycle (registry + `logs:subscribe`/`logs:unsubscribe`/`logs:flush` handlers) is extracted into `src/log-stream-manager.js`; a child that is still the active stream for its socket now emits a single `logs:terminal` event on exit (code 0 → `exited`, nonzero/signal → `crashed`, failed spawn → `error`), deduplicated so an error immediately followed by close still yields exactly one notification, while a deliberately killed child (explicit unsubscribe, replacement resubscribe, or socket disconnect) is removed from the registry synchronously so its later close is a no-op and never fires a spurious terminal event. `useLogStream.js` clears `subscribed` on `logs:terminal`, retains the reason for display, and exposes an explicit `retry()` (no auto-respawn loop); `LogViewer.jsx` shows a Stopped/Crashed/Error status with a Retry button instead of a misleading Streaming indicator. - **[issue-441] Deleting a fund defined in the base `config.json` no longer resurrects on the next config load** — `saveConfig` in `src/config-utils.js` persists only `computeDiff(base, merged)`, and `computeDiff` walks `Object.keys(modified)`, so a pair removed by `removeFund` was simply *absent* from `data/config.json` rather than recorded as deleted; the next `loadConfig` merged it straight back out of the base layer. `DELETE /api/:exchange/funds/:pair` returned `{success: true}` and the fund reappeared — affecting every fund an operator provisioned by editing `config.json` directly or that shipped in a deployment's base config (funds created through the UI live only in the override layer, so those deleted correctly). A blanket "base key missing from modified means deleted" rule was not an option: the config editor deliberately drops unknown/dead `regime` keys on the way through and they must stay inert in base rather than be tombstoned (`tests/exchange-routes-config.test.js`). Instead `removeFund` now writes a narrowly scoped tombstone — a `deletedPairs` string array at the exchange level, deliberately *outside* `pairs` so every writer that round-trips a block through `normalizeExchangeBlock` carries the marker forward and no ordinary save can resurrect the fund. `normalizeExchangeBlock` filters tombstoned pairs out of `pairs` at the single read chokepoint (covering `getFundsForExchange`, `getConfiguredFunds`, `getEnabledFunds`, `getEnabledExchanges`, `getFundConfig`), `getDefaultPair` skips them so a deleted fund can never become an exchange's default, and `updateFundConfig` clears a pair's tombstone whenever that pair is written so `addFund` re-adding a previously deleted pair is not suppressed. The marker is a plain JSON array, so `loadRawConfig`/`deepMerge` (arrays replace wholesale) round-trip it with no format awareness and older builds reading a tombstoned `data/config.json` just see an unknown key instead of throwing; configs with no deletions gain no new key. Added a `fund deletion tombstones` suite in `tests/config-utils.test.js` (delete → fresh-process reload → still gone, persisted-marker shape, default-pair selection, unrelated-save non-resurrection, re-add clearing, legacy flat blocks, malformed `deletedPairs` values) and a full `DELETE` → reload → still-gone route regression in `tests/exchange-routes-lifecycle.test.js`.

- **[issue-428] Coinbase order-placement body reads now stay within the request's abort deadline** — `makeRequest` in `src/adapters/coinbase/api.js` previously cleared its 30s `AbortController` timer right after `fetch()` returned headers, so both the error-body and success-body `response.json()` reads ran unbounded — a reset or stalled body after a 2xx placement response could hang forever with no application deadline, bypassing the `unknownOutcome`/reconciliation path entirely. - **[issue-429] Backup restore now drains every remaining writer, invalidates stale caches, and gives the operator a visible `force` control** — Completes the quiescence work started in #481. The maintenance lock stopped *new* mutations but never joined work that was already running, so a scheduled DCA cycle in flight when the lock was taken kept writing `regime-state.json`/`fill-ledger.json` straight through the copy; `src/pending-writes.js` now tracks every in-flight gateway write and `runIntervalCycle`/`executeConsolidation` are exported through it, so the coordinator waits for them and reports `gateway:pending-writes-in-flight` as a blocking `writers-not-quiesced` reason (HTTP 409, zero destination file changes) when they outlast the drain window. The gateway's sentinel writer is now drained and reloaded alongside UpDown — `loadState()` in `src/sentinel/sentinel-service.js` fully replaces in-memory state instead of merging into it and is exposed as `reloadState()`, so a post-restore `dismiss`/`clear` can no longer write the pre-restore alert list back over the recovered file. `src/restore-coordinator.js` now takes a uniform `gatewayWriters` list (stop before the copy, resume in reverse after it) rather than special-casing UpDown. Surviving in-memory views of the replaced files are dropped before the maintenance lock is released: `invalidateConfigCache()` in `src/config-utils.js` (so the merged config is never served from a pre-restore snapshot regardless of mtime resolution) and `candleCache.invalidate()` in `src/candle-cache.js` (which clears every aggregator and volume baseline, then reseeds in the background — the engines that would otherwise refill it are deliberately left stopped). Engine processes are now maintenance-aware: the gateway opens a window over the new built-in `engine:maintenance` IPC channel before it asks anything to stop and closes it on every exit path, and `src/ipc/ipc-server.js` refuses any channel outside the read-only/stop allowlist in `src/engine-maintenance.js` while it is open — registered centrally so all three engines are covered identically. The window always expires on its own (15 min default, 1 h ceiling) so a gateway that dies mid-restore cannot leave an engine permanently unable to trade. `admin/src/components/BackupRestore.jsx` now surfaces a blocked restore: the 409's `unconfirmed` writers are listed by name and reason, with a **Force Restore Anyway** button gated behind an explicit "I have verified the listed writers are not running" acknowledgement, and a forced success is reported as a warning rather than a clean restore. `tests/restore-writer-quiescence.test.js` grows to 41 cases, including a real IPC server/client round-trip proving a mutating channel is refused while a read and `regime:stop-all` still answer.
- **[issue-429] Backup restore now requires confirmed writer shutdown before it overwrites anything** — `POST /api/backups/:filename/restore` previously swallowed every rejected `regime:stop-all`, substituted an empty stopped list and restored anyway, reporting `success: true` while a surviving engine could overwrite the recovered files with its pre-restore snapshot. The route is now a thin adapter over `src/restore-coordinator.js`, which requires a positive `{ success: true, stopped: [...] }` acknowledgement from every *configured* exchange — a rejection, IPC timeout, disconnected client, negative or malformed reply returns HTTP 409 `writers-not-quiesced` with zero destination file changes (`{ "force": true }` in the request body is an explicit operator override for an already-dead engine). `src/engine-stop-all.js` (used by `regime:stop-all` in `engines/coinbase-engine.js`) now reports per-fund stop failures and keeps a failed engine in `regimeEngines` with its resume flag intact instead of clearing the whole registry and claiming success; `stop()` in `src/regime-engine.js` moved its timer/websocket teardown into a `finally` so a throwing state save can no longer leave a "stopped" engine still ticking. - **Completed trades are filed under the cycle they actually belong to, and dated by when they filled** - A take-profit fill that closes the last position ends the cycle, and the trade was recorded *after* that — so it was stamped with the cycle the fund had already moved on to, and timestamped when the engine booked it rather than when the exchange filled it. - **Live candle volume now uses the per-tick delta of the 24h ticker volume, not the raw 24h total** - `candleCache.processTick` was fed `market.volume24h` (the exchange's rolling 24-hour volume) as if it were the increment since the last tick, so `cur.volume += volume` added the entire 24h volume on every tick — ballooning all live (non-seeded) candle volumes and corrupting every volume-derived signal (VWAP, volume surge, OBV). - **Scorecard reload no longer double-counts neutral predictions** - `loadHistory` set `totalPredictions = predCount` (every `prediction` record, neutrals included), while the live `recordPrediction` path counts neutrals only as skips. - **`dcaStrategy` config-validator enum matches engine-supported values** - `EXCHANGE_CONFIG_SCHEMA.dcaStrategy.enum` was `['fixed','regime']`, but the engine only branches on `dcaStrategy === 'fibonacci'` ('regime' is never read). - **Macro daily-trend slope now measures a real daily trend** - `macro-regime` previously snapshotted the 20-day EMA every ~5-min update cycle and used that as the "previous day's EMA," so the slope term measured a 20-day EMA's movement over 5 minutes (≈0) — silently killing up to 20 points of macro-score range.
