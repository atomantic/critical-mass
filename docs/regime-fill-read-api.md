# Regime fill reads

`GET /api/:exchange/regime/fills` requires `paged=true`. Page size is capped at 100 rows; an omitted or false paging flag returns HTTP 400. The Transactions view uses this endpoint.

Transactions opts into bounded cycle options with `cycleOptionsPaged=true&cycleLimit=100&cycleOffset=0&cycleSearch=` on the same fills request. `cycleLimit` defaults to 100 and is capped at 100; offset defaults to zero. Both must be safe integers (positive limit, nonnegative offset). Search is a case-insensitive substring of the cycle ID, up to 200 characters. Options retain newest-cycle-first ordering; offsets beyond the result set clamp to its last page. Invalid options return HTTP 400.

In this mode `cycleIds` contains only the requested option page, excluding `current` (All and Current are fixed selector controls). `cycleOptionsInfo` contains `offset`, `limit`, matching `total`, `hasPrev`, and `hasNext`. The selected historical cycle remains available in the UI when it lies outside the option page. Search and option paging never change the exact `cycle` fill filter, row sorting, or full filtered summary. A historical ID can be passed as `cycle` even when absent from the current option page. Option pages and fills share the same revision; a stale `revision` still returns HTTP 409, and the client reloads fill page zero against the new revision while preserving the selected cycle and search.

Without `cycleOptionsPaged=true` (including explicit `false`), the prior contract is unchanged: `cycleIds` contains the complete cycle list, including `current` when present, and no `cycleOptionsInfo` is added. Transactions requests at most 100 options on each read (initial, filter change, or a pushed fund change); search and Previous/Next cycles browse another bounded option page.

Dashboard, Charts, and Cost Basis use `GET /api/:exchange/regime/fills/cycles`. The engine computes it from the same revision-cached fill snapshot as Transactions paging. `totalPnl`, `totalHoldback`, fill counts, and cycle counts cover the full ledger. Sell P&L follows the shared cycle pairing rules and counts each order-level annotation once across partial fills. Cost Basis cycle cost/proceeds retain the previous per-fill net-fee calculation.

The response includes at most 250 cost-basis cycles, 250 filled-order cycle summaries, 500 chart points, 500 recent detail fills, and 100 unpaired open-buy fills. `cyclesTruncated`, `fillCyclesTruncated`, `pnlPointsTruncated`, `detailsTruncated`, and `openFillsTruncated` report omissions. Large sell orders are omitted from details as whole groups. The UI keeps exact totals visible while labelling sampled or omitted details; it suppresses open-buy relation rows when their source fills are truncated.
